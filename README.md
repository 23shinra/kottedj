# Цифровая станция

**Интеллектуальная система планирования и оптимизации работы железнодорожной станции.**
Full-stack прототип: цифровой двойник станции, ИИ-планировщик на CP-SAT (Google OR-Tools), диспетчерский дашборд в реальном времени.

## Проблема
В часы пик к станции подходит больше поездов, чем она может принять: условно 200 при вместимости 100. Поезда стоят у входного сигнала без понятного срока ожидания и занимают перегон. Пути заняты «не теми» составами, локомотивы и бригады подаются по факту, когда поезд уже готов. Ручное перепланирование отнимает время и зависит от человека.

## Решение: управляемый поток вместо стихийной очереди
1. **Слоты прибытия (виртуальная очередь).** Оптимизатор назначает каждому поезду на подходе время приёма и конкретный путь. Если станция занята, поезд получает **рекомендованную скорость** или **удержание на предыдущей станции** вместо стоянки у сигнала. Это тот же принцип, по которому авиация управляет потоком через ground delay programs.
2. **Совместная оптимизация** (constraint-based scheduling, CP-SAT): пути с учётом длины, типа и электрификации, маршруты через горловины без пересечения стрелок, порядок по приоритетам, локомотивы и бригады с подачей **заранее**, к окончанию техобслуживания.
3. **Перепланирование при сбое меньше чем за 2 с**: три варианта считаются параллельно («Сбалансированный», «Пассажирские в приоритете», «Максимум пропускной»), у каждого виден прогнозный индекс. Лучший применяется автоматически, диспетчер может выбрать другой.
4. **Прогноз и рекомендации**: дефицит путей, ресурсов и задержки на час вперёд. Действия («открыть резервный путь 10», «направить №2032 по обходу», «вывести резервный локомотив») применяются в одно нажатие.
5. **Честное сравнение**: два цифровых двойника работают параллельно на одном и том же потоке поездов и сбоев. Первый ведёт реактивный диспетчер «первым пришёл — первым обслужен» (FCFS), второй исполняет план ИИ. Разница видна в UI в реальном времени.

## Результат (бенчмарк, 12 модельных часов, три пика «спрос ×2»)
Оба двойника получают один и тот же график и одни и те же сбои. Перепланирование раз в минуту, лимит решателя 1 с.

| Показатель | Без ИИ (FCFS) | С ИИ | Изменение |
|---|---:|---:|---:|
| Среднее ожидание приёма | 28,8 мин | 11,1 мин | **−61%** |
| Ожидание приёма, p90 | 82,4 мин | 34,1 мин | −59% |
| Максимальное ожидание приёма | 120,4 мин | 78,9 мин | −34% |
| Остановки у входного сигнала | 114 | 24 | **−79%** |
| Средняя задержка отправления | 21,8 мин | 5,5 мин | −75% |
| Задержка пассажирских | 25,9 мин | 2,9 мин | **−89%** |
| Ожидание локомотива или бригады | 4,8 мин | 3,1 мин | −35% |
| Отправлено поездов | 134 | 143 | **+7%** |
| Средний индекс станции | 63,9 | 79,3 | +24% |

Решатель CP-SAT: в среднем 1024 мс, p95 1080 мс, максимум 1779 мс. При сбое три варианта плана приходят в UI примерно за 2 с (требование кейса — 5 с). Воспроизвести: `make bench`, полный результат лежит в `bench/results.txt` и `bench/results.json`.

## Быстрый старт
Нужен Docker с Compose v2.
```bash
cp .env.example .env        # секреты и пароли задаются только через переменные окружения
make up                     # или: docker compose up -d --build
```
| Что | Адрес |
|---|---|
| Дашборд диспетчера | http://localhost:8080 (`dispatcher` / `dispatcher`, `admin` / `admin`) |
| Swagger / OpenAPI | http://localhost:8000/docs |
| Grafana (метрики) | http://localhost:3000 |
| Prometheus | http://localhost:9090 |
| Health-check | http://localhost:8000/api/health (а также `:8001`, `:8002`, `:8003` `/health`) |

Демо без backend: http://localhost:8080/?mock=1.

### Сценарий демонстрации
1. Войти как `dispatcher`. Индекс, схема станции, Гант и очередь на подходе обновляются в реальном времени.
2. Переключиться в режим **«Сравнение»** и сравнить живые KPI двойников FCFS и ИИ.
3. **Нештатная ситуация → закрыть путь** (или задать опоздание поезда, отказ локомотива). Примерно через 2 с придут три варианта плана с прогнозным индексом и временем расчёта. Лучший уже применён, другой можно применить вручную.
4. Принять рекомендацию, например «Открыть резервный путь 10», и посмотреть, как меняется индекс.
5. **«Стресс ×10»**: несколько одновременных сбоев и поток телеметрии в 10 раз чаще. На индикаторе задержки UI видно, что она остаётся меньше 500 мс.
6. Перемотать историю на 5–15 минут назад слайдером, затем выгрузить **отчёт PDF или CSV**.
7. Остановить симулятор (`docker compose stop simulator`): появится плашка «Нет связи». После `docker compose start simulator` связь восстановится сама.
8. Войти как `admin` → «Настройки»: изменить веса индекса или лимит решателя. Изменения применяются без перезапуска.

Автоматическая проверка того же сценария: `make demo`.

## Архитектура
Подробно: [docs/architecture.md](docs/architecture.md). Контракт API: [docs/api-contract.md](docs/api-contract.md).

```
simulator ─WS─▶ ingest ─▶ Redis Streams ─▶ planner (CP-SAT)
  ▲  2 двойника     валидация, дедуп,    │      план, варианты,
  │                 сглаживание          ▼      рекомендации
  └── commands/plan ◀──────────────── api (FastAPI) ──WS──▶ frontend (React)
                                       │  REST, JWT, отчёты
                                       ▼
                                 TimescaleDB (история 72 ч)   Prometheus + Grafana
```

| Требование кейса | Где реализовано |
|---|---|
| Модель станции: пути, платформы, стрелки, парки | `config/station.yaml`, `shared/dstation/station.py`, SVG-схема |
| Планирование: очерёдность, пути, локомотивы, бригады | `shared/dstation/planner/cpsat.py` (CP-SAT), `greedy.py` (fallback) |
| Индекс 0–100 и A–E, веса, пороги, top-5 | `config/index.yaml`, `shared/dstation/index.py` |
| Конфликты: маршруты, занятость, ресурсы | `shared/dstation/planner/analysis.py` |
| Перепланирование при сбоях с вариантами | `services/planner/main.py`, `planner/core.py` |
| Поток от 1 Гц, буферизация, дедуп, валидация, сглаживание | `services/simulator`, `services/ingest` |
| Reconnect, backoff, «нет связи» | `services/ingest/main.py`, WS-клиент фронтенда |
| Шина событий | Redis Streams, `shared/dstation/bus.py` |
| История 24–72 ч, перемотка, отчёт PDF/CSV | `infra/db/init.sql`, `services/api/store.py`, `reports.py` |
| Конфигурация без перекомпиляции | YAML + `PUT /api/config/*` (БД, Redis) |
| Логи, метрики, health-check | structlog JSON, `/metrics`, `/health`, Grafana-дашборд |
| Аутентификация и ограничение доступа к настройкам | JWT, роли `dispatcher` и `admin` |
| OpenAPI | http://localhost:8000/docs |
